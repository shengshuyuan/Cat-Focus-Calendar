> 适用范围：本仓库的 ESP32-C3 FoloToy AI Passport 固件开发、增量烧录和实机验收。
> 本文记录已经验证过的工程经验；新问题按文末模板追加，不覆盖旧证据。

## 1. 这块板子的固定前提

- 主控是 ESP32-C3，8 MB Flash，**没有 PSRAM**。显示、LVGL、音频 DMA、Wi-Fi/BLE 和任务栈共同竞争内部 RAM。
- 屏幕是 ST7789P3，240 × 320，RGB565，SPI2，当前 UI 按竖屏设计。三颗按键共用 GPIO0 的 ADC 分压，阈值以 `components/bsp/include/bsp_pins.h` 为准。
- 音频链路使用 ES8311，电池计量使用 CW2017。GPIO、I2C 地址、SPI 参数和按键窗口不能从通用 ESP32-C3 开发板资料推断。
- `partitions.csv` 中的 `cardid` 位于 `0x356000`、大小 16 KB，是受保护的设备身份分区。开发固件不能擦除、移动或覆盖它。
- 当前项目使用 ESP-IDF 5.5.3。macOS 上应优先使用 `$HOME/esp/esp-idf-v5.5.3`，并把 `/opt/homebrew/bin` 放在 PATH 前面，避免 `idf.py` 选到错误的 Python 环境。

## 2. 开发时必须遵守的原则

1. **先核对板级事实，再写功能。** 先读 `AGENTS.md`、本目录硬件指南和 `bsp_pins.h`；改引脚或总线时同时更新文档，并记录实机结果。
2. **把内存当成功能约束。** 像素风页面如果把每个像素都建成一个 `lv_obj`，对象数量会快速增长。评估页面时同时看 LVGL pool、LCD DMA、I2S DMA、任务栈、总空闲堆和最大连续块。
3. **LVGL 只能在正确的上下文访问。** LVGL 定时器回调可以直接操作对象；按键任务或其他工作任务必须使用 `bsp_lvgl_lock()` / `bsp_lvgl_unlock()`。删除页面前先停计时器和工作任务，再清空静态对象指针。
4. **慢操作移出 UI 回调。** Wi-Fi 连接、NTP、BLE 配网、音频读写和大块分配不能放在按键回调或 LVGL 任务中；工作任务只把结果带回 UI。
5. **网络功能要有离线降级。** 农历和节气采用生成后的静态表，设备运行时不依赖 Python 或网络；网络只负责校时和后续刷新，不应让日历页面因断网不可用。
6. **区分“代码通过”和“实机通过”。** 静态检查、主机测试、编译、烧录和串口启动日志只能证明对应层级；屏幕布局、实体按键手感、手机 BLE 配网和不同电量下的 ADC 阈值必须单独实机验收。
7. **增量烧录优先。** 已配网或已有身份数据的设备只使用 `idf.py build/flash` 的增量路径；不要使用 `erase-flash` 或把合并镜像当成擦除操作。

## 3. 已遇到并解决的问题

### 3.1 像素风 UI 触发 LVGL 内存池耗尽

- **症状**：切换到像素风番茄钟页面时，在创建 `button_glyph` 或像素数字对象期间出现 `Guru Meditation Store access fault`，随后设备重启。
- **原因**：每个像素方块都是 LVGL 对象，页面同时保留日期标签；原始 24/32 KB LVGL pool 不足。ESP32-C3 没有 PSRAM，故障表现为对象创建阶段的内存访问错误，而不是“页面只是不显示”。
- **修复**：把 `CONFIG_LV_MEM_SIZE_KILOBYTES` 调整到 128 KB；先移走旧的 `sdkconfig` 再重新配置，不能只改 `sdkconfig.defaults` 后直接假定生效。UI 仍需控制对象数量，不能把扩大 pool 当作无限内存。
- **验证**：64 KB 仍会崩溃；128 KB 版本重新编译、增量烧录后，串口稳定进入 `Ready: buttons=1 battery=1`，未再出现重启。
- **剩余风险**：128 KB 会占用更多内部 RAM。加入音频、TLS、双缓冲或更多动画前，必须重新检查最大连续堆和 I2S DMA。

### 3.2 固定插画不应当做运行时场景图

- **症状**：第一版把猫、绿植、书、山景和状态图拆成少量大色块，视觉上明显不像已确认的设计稿，同时仍创建了大量 LVGL 对象。
- **原因**：把固定视觉素材当成运行时布局拼接，而不是先按屏幕尺寸制作像素插画。继续增加色块会同时增加对象数和内存压力，却无法恢复设计稿的细节。
- **修复**：从已确认设计稿中按 240 × 320 屏幕尺寸裁取固定插画，再转为 RGB565 LVGL 描述符。`main/assets/` 现在包含番茄钟下半部、万年历山景和万年历猫的 Flash 资源；时间、日期、农历、选中态、电量、Wi-Fi 和按键状态仍由代码实时绘制。
- **验证**：固件构建大小为 `0x1a28b0`，3 MB 应用分区还剩 `0x15d750` 字节。插画使用 Flash，不再在 LVGL 内存池中创建同等规模的对象图。
- **剩余风险**：设计稿截图与实体屏幕在纸张底色、像素位置上可能有轻微差异；在取得实体屏幕照片前，不能声称视觉验收完成。

### 3.3 农历显示曾经只是占位文本

- **症状**：日历页只显示硬编码的“农历 八月初九”，并把联网状态写成“待联网”；这既不能随月份变化，也没有真正进入万年历详情。
- **原因**：UI 原型先于日期模型完成，且把网络数据源误当成运行时必需依赖。
- **修复**：使用 `lunar-python` 1.4.8（MIT）在开发机生成 1900-01-01 至 2100-12-31 的轻量 C 表，固件只链接 `main/lunar_table.c/.h` 和 `main/calendar_model.c/.h`，运行时不带 Python、不请求第三方 API。联网只用于 SNTP 校时；没有网络时继续使用已知日期和静态农历数据。
- **边界证据**：主机测试验证了 2026-09-09 为农历七月廿八、2024-02-10 为正月初一、2023-03-22 为闰二月初一，并验证了节气索引。以后修改生成器必须重新生成表并重跑这些边界测试。
- **产品含义**：第三方库适合作为离线构建时的数据源，不适合把完整 Python 运行时塞进这块板子；表范围、授权和生成命令必须写在源码头部。

### 3.4 BLE 配网初始化过早释放了蓝牙内存

- **症状**：启动时为了判断是否已配网而初始化 BLE 配网管理器，随后以 `WIFI_PROV_SCHEME_BLE_EVENT_HANDLER_FREE_BTDM` 释放 BTDM；日志显示蓝牙内存已释放，后续再进入配网页存在生命周期风险。
- **原因**：把“读取已保存 Wi-Fi 配置”和“启动 BLE 配网服务”混成了一个流程。
- **修复**：启动阶段直接通过 `esp_wifi_set_mode(WIFI_MODE_STA)` + `esp_wifi_get_config(WIFI_IF_STA)` 判断 NVS 中是否有 SSID；只有用户真正进入配网页时才调用 `wifi_prov_mgr_init()` 并启动 BLE。当前开发版本使用 `WIFI_PROV_SECURITY_0`，手机填写家庭 2.4 GHz SSID/密码，凭据由 ESP-IDF Wi-Fi NVS 保存。
- **网络行为**：连接成功后请求 `ntp.aliyun.com` 和 `pool.ntp.org` 校时；断网时保留本地时间/农历能力。正式发布前应切换到带设备 PoP 的 Security 1，并在手机端验证重复进入、错误密码和退出流程。

### 3.5 保护分区让“整片擦除”变成高风险操作

- **症状**：固件可以正常编译，但如果按普通 ESP32 项目执行整片擦除或写入不匹配的合并镜像，可能破坏 `cardid`。
- **原因**：本项目不是双槽 OTA；应用、NVS、PHY data 与受保护身份分区在固定地址上，开发动作必须尊重分区布局。
- **修复**：`tools/validate.sh --firmware` 检查 `cardid@0x356000` 和合并镜像；日常开发只做增量 `idf.py flash`。刷写前保留串口日志和分区表证据，禁止 `idf.py erase-flash`。
- **验证**：当前固件应用大小约 1.66 MB，小于 3 MB factory 上限；受保护布局检查和合并镜像检查均通过。

### 3.6 整屏串口截屏超出当前内存预算

- **症状**：当前应用在启用 Wi-Fi 时不能同时运行 240 × 320 RGB565 整屏截屏，因此刷新后的页面没有串口导出的真机截图。
- **复现**：`FAP_SCREENSHOT_V1` 需要一块 `240 × 320 × 2` 字节的帧缓冲（153,600 字节），还要与 LVGL、Wi-Fi/BLE、音频和应用分配共用内部内存。
- **证据**：`main/fap_screenshot.c` 明确保持协议禁用，`sdkconfig.defaults` 记录面向截图的 LVGL 分配配置；仓库中的页面图片已明确标为渲染效果图。
- **根因**：ESP32-C3 没有 PSRAM，大块连续帧缓冲无法在带 Wi-Fi 的交互应用中安全共存。
- **修复**：本构建保留串口截屏协议禁用状态，使用可追溯到已入库布局与资源的渲染效果图发布；不得把它们标为真机截图。
- **自动化验证**：实现和文档修改通过 `git diff --check`。
- **真机验证**：本次修订尚未执行；真实屏幕行为和闲置背光唤醒仍待设备验收。
- **剩余风险**：渲染效果图与实体 LCD 的纸张底色、像素位置或控制器行为可能不同；视觉验收仍需要实体照片或真实截屏。

## 4. 当前工作流

1. 在 `feature/*` 分支上做小步修改，先阅读板级文档和源代码事实。
2. 先跑主机侧模型测试和 `tools/validate.sh --static`，再编译；涉及分区或镜像时补跑 `--firmware`。
3. 真机验证至少记录：固件版本、烧录方式、串口启动结果、屏幕/按键结果、Wi-Fi/BLE 状态，以及是否保留原有身份数据。
4. 新增问题先定位根因，再把证据写入本文；修复后补一个自动化检查或明确的手工验收步骤。
